# 日後雲端同步及 AI 升級

目前 App 使用真正的 IndexedDB，所有主要功能已可在本機操作。這份文件是升級方案，不代表這些服務已經啟用。

## 儲存介面

`src/store.tsx` 負責使用者狀態；資料庫操作只在 `src/lib/storage.ts` 的 `loadStoredData()`／`saveStoredData()`。介面元件透過 `useCookbook()` 更新資料，不直接操作資料庫。`AppData` 包含穩定 ID、版本、食譜、收藏、分類、購物、實際日期計劃及煮食進度；`validateAppData()` 會驗證結構和關聯。可加入遠端 adapter 及登入狀態，同時保留 IndexedDB 作離線快取。

## Supabase

首次可採用每人一筆 cookbook JSONB 記錄，避免立即改寫所有介面；使用量增加後才按食譜、食材、步驟、分類、購物及餐點拆表。記錄至少包含 `owner_id`、`data`、`version`、`updated_at`。每次寫入需用版本條件避免舊資料覆蓋新資料，遇衝突先保存本機副本再讓使用者決定如何合併。

必須啟用 Row Level Security，以 `auth.uid() = owner_id` 限制讀寫，並以帳戶 ID 區隔本機快取。不能因為知道記錄 ID 就能讀取其他人的食譜。登入／登出時不可把其他帳戶資料混在同一份快取。

圖片可從目前的 data URL 遷移到私人 Supabase Storage bucket，透過短期簽署網址讀取；RLS 同時限制檔案擁有人。JSON 備份仍須將圖片包入，避免備份只留下已過期的簽署網址。公開 publishable key 可以放在前端設定；service role key 只可在伺服器使用。

設定前需要選擇 Supabase 專案及登入方式，檢查免費方案容量／流量／停用政策或付費方案。這個版本沒有任何 Supabase 帳戶設定或費用。

## AI／圖片／網址匯入

前端可沿用已建立的「整理 → 編輯確認 → 儲存」流程。AI 整理及 OCR 請求應透過伺服器處理，API Key 不能寫進前端 bundle。回傳結構仍須經 schema 驗證。

圖片辨識需要保留原始影像、原始數字與不確定標示，不清楚的份量、溫度及時間不得猜測；日文翻譯應保留原文以便核對。每次顯示將傳送甚麼內容，讓使用者知道模型供應商及估計費用。

網址擷取需要伺服器驗證 URL、防止 SSRF，禁止私人／回環位址與 DNS 重新綁定，限制下載大小、重新導向與逾時。優先解析 Recipe JSON-LD，並保留來源連結；遵守來源網站的存取條件。內容不足時顯示需要補充的欄位，再交由使用者確認。

以上涉及第三方服務及可能的費用，尚未實作或啟用。目前的文字及 JSON-LD 匯入只在使用者瀏覽器處理。
